# 初始需求分析（SRS 分析）

> 对应指导书 3.2 节初始业务需求与附录 B。本文只做**需求→设计与实现**的映射，不重复抄写原文。

## 1. 角色与边界

| 角色 | 能力 | 本版本不做 |
| --- | --- | --- |
| 学生 Student | 浏览活动、报名（直接/审核/候补）、取消自己的报名、查看站内消息 | 注册、找回密码、修改个人信息、多人协作 |
| 管理员 Admin | 发布活动、下架活动（软删除）、审批报名、查看通知失败留痕 | 复杂权限体系、组织架构、审批流引擎、数据导出 |

固定演示账号（指导书 B.1 明确无需注册与复杂权限）：三名学生 + 一个管理员口令。

## 2. 业务规则 → 设计落点

| 编号 | 业务规则（B.2） | 落在哪里 | 关键实现 |
| --- | --- | --- | --- |
| R1 | 直接报名：名额充足即“已通过”并通知 | `DirectRegistrationPolicy.submit` | 调 `CapacityRule.ensure_available`，返回 `approved` |
| R2 | 审核报名：提交为“待审核”，管理员批准/拒绝 | `ApprovalRegistrationPolicy` + `ApprovalService` | 提交返回 `pending`；批准时二次检查名额 |
| R3 | 名额按“已通过”统计，待审核不占，满员不得再批准 | `CapacityRule`（唯一计数口径） | `count_by_status(approved)`；审批前 `ensure_available` |
| R4 | 同一学生对同一活动至多一条“待审核/已通过（候选补中）”的有效报名 | 服务校验 + 数据库唯一索引 | `find_active` + `ux_registration_active` 部分唯一索引 |
| R5 | 学生可取消自己的报名；活动开始后不得新增报名 | `RegistrationService.cancel` / `Activity.is_open` | 本人校验、状态机校验、活动时间校验 |
| R6 | 通知失败要留痕，但不得让已提交的报名消失 | 事务边界 + `notification_failures` | 报名事务提交后才发布事件；通知异常逐渠道捕获并落库 |
| R7 | 数据持久化；删除活动可选“拒绝删除”或“软删除” | `ActivityRepository.soft_delete` | 采用**软删除**：活动下架、历史报名与通知全保留，后台提示受影响条数 |

> R7 的选择理由：课程评分关注“数据可追溯”，硬删除会连带损失历史报名证据；软删除代价只是列表需过滤 `status='published'`，成本更低。

## 3. 领域对象识别

| 对象 | 职责 | 不负责 |
| --- | --- | --- |
| `Activity` 活动 | 自己是否还能报名（`is_open`）、名额上限、规则类型 | 谁报名、名额还剩多少（依赖仓储查询，避免实体持有仓储） |
| `Student` 学生 | 身份与联系方式 | — |
| `Registration` 报名记录 | 状态、策略来源 `policy_key`、审批人/时间、候补序号 | 名额计算、通知发送 |
| `RegistrationPolicy`（抽象） | 准入语义（通过 / 待审核 / 候补） | 名额计数实现、持久化、通知 |
| `CapacityRule` | 名额口径与“是否有空位” | 何时检查由调用方（策略/审批服务）决定 |
| `RegistrationService` | 报名/取消的编排与公共不变量 | 通知内容、页面渲染 |
| `NotificationService` | 事件→消息文案→多渠道投递 | 业务判定 |
| `EventBus` | 订阅与广播 | 任何业务语义 |

## 4. 非功能需求与实现

| 需求 | 实现 |
| --- | --- |
| 数据持久化 | SQLite 单文件，应用重启数据不变（T13 用“新建应用实例指向同一文件”验证） |
| 可理解的中文反馈 | 领域异常 `DomainError.message` 直接作为 flash 提示 |
| 不强制前端框架 | Jinja2 + 原生 CSS，无外部 CDN 依赖，离线可用 |
| 可复现测试 | `pytest`，每例独立临时数据库，30 项全绿 |
| 可部署 | waitress + nginx，`deploy/` 一键脚本；README 给出从零步骤 |

## 5. 关键假设（文档化，避免“藏着假设”）

1. 报名时间与活动开始时间均按服务器本地时区（部署说明中提示按 `Asia/Shanghai`）。
2. “活动开始后不允许新增报名”以 `start_time` 为界；取消报名不设时间限制（取消只会释放名额，风险更低）。
3. 审核型活动在名额已满时**仍允许提交**（进入待审核），因为 B.2 只禁止“满员后再批准”。这一点在设计中由策略表达，便于将来改为“直接拒绝”。
4. 邮件渠道在课程环境以落盘 `.eml` 模拟，不接真实 SMTP，避免凭据进入仓库。
