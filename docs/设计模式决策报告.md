# 设计模式决策报告

> 对应指导书 3.3 节设计任务 A–D 与 3.7 节证据要求。所有结论都有可执行测试或 git 差异作为证据。

## 1. 决策总览

| 决策点 | 选择 | 主要理由 | 代价 |
| --- | --- | --- | --- |
| 报名规则表达 | 策略模式（`RegistrationPolicy` 抽象 + 3 个实现） | 规则是唯一会反复变化的部分，且变化是“整条规则”而不是参数 | 多一层间接；每个策略需要写契约测试 |
| 名额检查归属 | 公共领域规则 `CapacityRule`，检查**时机**由策略决定 | 计数口径唯一、避免复制；时机又确实因规则而异 | 策略必须知道“何时调用”，耦合了一个调用约定 |
| 业务与通知解耦 | 观察者模式（`EventBus` + 订阅者） | 通知渠道会持续增加（站内信 → 邮件 → 短信），业务不应感知 | 事件顺序与失败语义需要显式设计（见第 4 节） |
| 通知渠道 | `NotificationChannel` 接口 + 逐渠道分发 | 渠道差异（落库 / 发信 / 短信）被隔离 | 每渠道各自负责去重与重试 |
| 事务边界 | 报名先提交，再发事件；通知失败只留痕 | 通知是“事后告知”，不应否决已成立的业务事实 | 通知可能延迟或失败（用留痕表 + 后台可见补偿） |
| 活动删除 | 软删除 | 保留历史报名与通知，可审计 | 列表/报名查询都要过滤 `status` |

## 2. 设计任务 A：职责与类图

见 `docs/UML类图.md`。要点：

- **领域对象**：`Activity`、`Student`、`Registration`；
- **业务服务**：`RegistrationService`（报名/取消编排）、`ApprovalService`（审批）、`ActivityService`（发布/下架）；
- **规则对象**：`RegistrationPolicy`（抽象）、`PolicyRegistry`（选择）、`CapacityRule`（名额口径）；
- **通知对象**：`EventBus`、`NotificationService`、`NotificationChannel` 实现。

职责边界的三条硬约束：
1. 实体不持有仓储、不发通知；
2. 服务不直接写 SQL（仓储负责）；
3. Web 路由不含业务判断（只做参数解析与错误翻译）。

## 3. 设计任务 B：策略模式与名额归属

### 3.1 抽象为什么是稳定的

三种规则（直接、审核、候补）回答的是同一个问题：**这次提交的结果状态是什么**。
所以抽象只有一个方法 `submit(context) -> PolicyDecision(status, message, queue_no)`。
`message` 让策略把“为什么这样判定”讲清楚，避免上层再拼装业务语义。

### 3.2 名额检查属于公共规则（结论 + 论据）

**结论**：名额的“计数口径”是公共规则；“检查时机”是策略责任。

论据：
1. 名额上限是 `Activity` 的固有属性，与“是否审核”无关；
2. 若把检查写进每个策略，三种规则会各写一份 `SELECT COUNT(*)`，口径一旦改（例如将来“候补也占名额”）需要改三处；
3. 但检查时机确实不同：直接报名必须提交时检查（满员就拒绝），审核报名提交时不能检查（待审核不占名额），候补报名满员时也不能拒绝（要入队）；
4. 因此拆成“无状态规则 `CapacityRule` + 由策略调用”，既保证单一实现，又保留规则差异。

### 3.3 主流程里没有类型判断（可验证）

`RegistrationService.register` 中不存在 `if activity.registration_mode == ...`，只有 `policy = registry.for_mode(activity.registration_mode)`。
新增候补规则时，`RegistrationService` 只改了 8 行（发布事件类型的选择），没有新增任何分支逻辑。

## 4. 设计任务 C：解耦报名与通知

### 4.1 结构

```
RegistrationService ──publish──► EventBus ──handle──► NotificationService ──deliver──► 渠道
                                     └──────handle──► WaitlistPromotionService（v2）
```

### 4.2 通知失败是否影响报名事务

**不影响**，且这是刻意设计：

1. `register()` 先 `BEGIN → INSERT → COMMIT`，事务结束；
2. 事务提交后才 `bus.publish(event)`；
3. `NotificationService.handle` 对每个渠道 `try/except`，失败写 `notification_failures`（独立连接、独立事务）；
4. `EventBus` 还有一层 `error_listener` 兜底，防止订阅方整体崩溃。

测试证据：`test_t11_notification_failure_is_recorded` 注入一个必失败的渠道，断言“报名记录存在 + 失败留痕 + 站内消息仍送达”。

### 4.3 如何避免重复通知

- `event_key` 由事件类型 + 报名 ID（+状态）构成，例如 `approved:12`；
- `notifications` 表 `(event_key, channel)` 唯一索引 + `INSERT OR IGNORE`；
- 邮件渠道先落盘再登记，登记过的直接跳过。
- 测试证据：`test_t12_notification_is_idempotent`（重复 publish 两次，只产生 1 条）、`test_v3_email_channel_*`（邮件也只 1 封）。

## 7. 客观代价（如实报告）

1. **文件数与间接层增加**：一个报名请求会经过路由 → 服务 → 策略 → 规则 → 仓储 → 事件总线 → 通知 → 渠道，链路长，新人上手需读 3 个文件才能看懂一次报名。
2. **契约测试成本**：策略抽象必须靠测试保证行为一致，否则“抽象”退化成三份不同语义的实现。
3. **事件顺序隐式约定**：`NotificationService` 与 `WaitlistPromotionService` 都订阅取消事件，顺序决定了通知文案是否包含“已转正”信息；本项目通过“转正后再单独发一条通知”规避顺序依赖。
4. **软删除带来查询成本**：所有活动查询都要带 `status` 过滤，漏写就会出现“已下架活动仍可报名”的缺陷（当前由 `_require_activity` 统一兜底）。
