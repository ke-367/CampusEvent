# 需求变更影响分析

> 对应指导书 3.5 节。变更实现见 Git 标签 `change-v2`（提交 `3537366`，合并 `6fb9751`）。

## 1. 变更需求

| 编号 | 变更内容 | 来源假设 |
| --- | --- | --- |
| CR-01 | 新增**候补报名**规则：名额满时可进入候补队列；有人取消时按顺序自动转正并通知 | 用户提出（3.5 节场景） |
| CR-02 | 新增**邮件通知渠道**：站内信之外，关键报名事件同时投递邮件 | 用户提出 |

变更前必须回答的问题：**这条变更会不会打穿设计？** 下面的分析用来证明“只会局部扩展”。

## 2. 变更前的影响预判（设计阶段完成，未写代码）

| 变更点 | 是否影响现有类 | 预判结论 |
| --- | --- | --- |
| 新增第三种报名规则 | `PolicyRegistry`（注册一处）、`Registration.status` 取值集合 | 不改 `RegistrationService` 主流程，若必须改也只是一行事件类型选择 |
| 候补需要位次 | `Registration` 增 `queue_no` 字段 + 迁移 | 需要数据迁移，但不动既有字段语义 |

| 邮件需要去重 | `notifications` 表已有 `(event_key, channel)` | 渠道名不同即天然隔离 |

**风险清单与对策**

| 风险 | 对策 | 结果 |
| --- | --- | --- |

| 邮件记录污染学生“我的消息” | 消息查询默认 `channel='inapp'` | 开发中踩到并修复（第 5 节问题 2） |
| 活动开始后仍转正，等于变相新增报名 | 转正前判断 `activity.is_open` | V5 验证 |

## 5. 变更过程中真实遇到的问题（含定位与修复）

**问题 1：候补报名触发的是数据库错误而不是业务错误**

- 现象：同一学生第二次候补同一活动时，抛 `sqlite3.IntegrityError`，页面 500。
- 定位：`RegistrationRepository.find_active` 的 `WHERE status IN ('pending','approved')` 没包含 `waitlisted`，所以服务层“重复报名”校验通过，最终撞上唯一索引。
- 修复：`find_active` 与 `count_for_event` 口径同步加入 `waitlisted`；并新增 V4 用例固定该行为。
- 教训：**状态集合散落在多处 SQL 里**是隐患。变更后把“有效报名状态”收敛成一个仓储常量。

**问题 2：邮件投递记录被当成“学生消息”显示**

- 现象：报名一次后，“我的消息”出现两条一模一样的通知，未读数翻倍。
- 定位：`list_for_student` 未按渠道过滤，把 `channel='email'` 的投递记录也渲染成站内消息。
- 修复：查询默认 `channel='inapp'`（`unread_count`、`mark_all_read` 同步）。
- 教训：**同一张表承载两种语义（投递台账 vs 用户消息）**时，渠道过滤必须是查询的第一条件，最好用默认参数强制。

**问题 3：邮件断言从“报名成功”改为“成功报名”**

- 现象：邮件渠道测试断言正文包含“报名成功”失败。
- 定位：`.eml` 的标题做了 RFC2047 base64 编码，正文里实际是“成功报名”，断言写错。
- 修复：断言改为解码后的客观文案，并断言 `.eml` 文件存在于 `outbox/`。
- 教训：验证“通知真的发出去”要看**产物**（文件、记录），而不是猜字符串。

## 6. 结论

1. 变更被三种机制吸收：**策略槽位**（CR-01 的规则）、**事件订阅位**（CR-01 的转正）、**渠道接口**（CR-02 的邮件）。
2. 唯一的“必要重构”是 `NotificationService` 的渠道化——因为 baseline 把渠道写死在一个方法里；这正是“过早具体化”的代价，也是本次变更最值得记录的教训。
3. 回归 30/30 通过、核心类改动 8~69 行、主流程零新增分支，说明设计在“可扩展”这一维度是达标的；同时文件数与调用链增加，是可读性付出的代价。
